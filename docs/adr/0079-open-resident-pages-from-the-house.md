# 0079. 会話する配置は家に住み、承認は家で答え、個人のページは家から開く

- Date: 2026-11-28
- Status: Accepted

## Context

家には部屋の会話があり、各配置の Web UI には個別の会話がある。家の住人のリンクはその個別の会話を開く。各配置の Web UI は、同じ入口で記憶、活動の記録、モデルの設定も扱う。会話の入口は一つにしたいが、オーナーは引き続き配置ごとの記憶を直し、活動を調べ、モデルを選ぶ。家と各配置の backend はログインのセッションを別々に持ち、各 backend の手前には gated がある。

最初の家にはペネロペ・なつみ・アキ・さやかが住み、ミャオは家のプラグインとコネクタを持たない配置だった。会話を家に集めるにあたり、ミャオもほかのエージェントと同じ入口にそろえる。

Sentinel の承認は未実装だが、当初の設計では配置ごとの Web UI が承認の入口だった。会話の入口を家に移すなら、オーナーがその住人の承認待ちを見て答える場所も決めておく必要がある。

## Decision

### 1. 個人のページには、オーナーが扱う設定と記録を残す

- 各住人の個人のページへのリンクを家に出す。個人のページには、記憶の閲覧・編集・復元、活動の記録、モデル設定を残す。会話の画面、メッセージ送信・会話履歴、会話の要約の流れと既読をなくす。活動の記録にある失敗の「見た」は会話の既読とは別なので残す。
- 配置ごとの会話を通知する Web Push は、会話の入口とともに廃止する。家に Web Push は追加しない。iPhone の会話と通知は家を使う。以前の会話を家に取り込むためのエージェント側の DB 移行は行わない。以前の会話は、家の履歴としては表示しない。

### 2. 個人のページは従来どおり、その配置でオーナーを確かめる

- 家は GitHub OAuth で登録済みの人を確かめる。個人のページへのリンクは、配置が登録した HTTPS の行き先を開くだけとする。家の cookie・token・GitHub の認証情報をリンク先へ引き継がない。
- リンク先は gated の入口と、backend の既存のオーナー確認を使う。リンク先の有効なセッションがあれば再ログインしない。なければその配置でログインする。家に入れるというだけでは、記憶・活動の記録・設定の閲覧や変更を許さない。
- 守る対象は、各配置の記憶・活動の記録・設定と、それぞれの認証情報である。リンクの設定が無いか有効な行き先と確認できないときはリンクを出さない。リンク先でオーナーを確かめられなければ、個人のページとその API はアクセスを断る。

### 3. `reply` でオーナーと話す配置は家に住む

- `reply` でオーナーと話す配置は、すべて家の住人にする。家の受信プラグイン、コネクタ、Sentinel の登録をそろえる。
- この決まりをミャオにも適用する。ミャオも家に住み、家と Slack で話す。

### 4. 承認はその住人との 1 対 1 の欄で答える

- Sentinel の承認を実装するとき、オーナーは家で、その住人との 1 対 1 の欄から許すか断るかを選ぶ。承認の答えは発言として送らず、エージェントの入力にも通さない。発言を送れる居場所の条件は承認の権限とは別である。
- 勧める方式は、配置の receivers の家のプラグインが承認待ちを家に送り、家から答えを取る形である。プラグインは backend を経由して Sentinel に届き、Sentinel の管理口は receivers に開かない。家は各配置の管理口を呼ばない。承認待ちの正と許可の判定は Sentinel に残す。
- 家の画面で承認待ちを見て答えられるのは、その住人に結び付いたオーナーだけである。オーナーを認証できない、答えを承認待ちに結び付けられない、または家から答えが届かないときは、通信を通さない。

### 本 ADR で決定しないこと

- 承認待ちと答えを運ぶ方式、新しい承認待ちをオーナーに知らせる方法は、承認を実装するときの ADR で決める。承認の欄の開き方と画面、答えを取り込む契約の詳細は [家の仕様書](../house.md) と [Sentinel の設定仕様](../sentinel-config.md) に委ねる。
- 個人のページの画面構成・パス、家のリンクの設定形式（委譲先: [UI 向けの API の仕様書](../ui-api.md) と [家の仕様書](../house.md)）。
- 個人の部屋の名前・説明・定員（委譲先: 配置リポジトリの家の設定）。
- 補助画面の配置（委譲先: [家の仕様書](../house.md) の「人の画面」）。

## Consequences

- 会話の入口は家になり、配置ごとのページを会話のために開く必要がなくなる。設定や記録を開くときは、配置ごとにログインを求められる場合がある。
- 家の認証障害で会話が開けなくても、オーナーはリンク先を直接開いて記憶・活動の記録・設定を扱える。逆に、各 backend に入れなくても家の会話は読める。
- 旧 Web UI の会話履歴、ブラウザー通知の購読、既読は家の会話に持ち越さない。配置ごとの Web Push を廃止してから家の iPhone アプリが出るまで、1 対 1 の返事の通知がないことをオーナーは受け入れる。
- 勧めた承認の方式では、家が侵害されると、つながっているすべての配置に対してオーナーを装った承認の答えを出され得る。個人のページの認証を分けても、承認の入口を家に置くことによるリスクは残る。

## Alternatives Considered

- **家の認証を各 backend が信頼する**: 初回のログインを減らせる一方、家が発行する資格を各 backend が検証し、宛先と失効を管理する必要がある。家の認証が記憶や設定まで開くことは避け、既存の境界を保つ。
- **配置ごとの会話の入口を残す**: 一つのエージェントに二つの会話が残り、どちらの履歴を見ればよいか変わらない。
