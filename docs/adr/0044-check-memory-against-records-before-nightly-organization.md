# 0044. 夜は記憶を原本と照合してから整理し、週に一度は棚卸しする

- Date: 2026-11-20
- Status: Accepted（一部を [ADR-0050 夜は記憶の見取り図を渡し、棚卸しで中身と構成を分けて見直す](0050-organize-memory-with-a-map-and-a-weekly-review.md) と [ADR-0051 照合と整理の基準は別々に持ち、成功したときだけ進める](0051-carry-unfinished-night-work-forward.md) で置き換え。夜の時刻を backend が持つ点は [ADR-0069 エージェントは `sleep` で自分で眠り、起きる時刻まで出来事を受け取らない](0069-sleep-by-her-own-call-until-a-wake-time.md) で置き換え）

## Context

夜は、日中のセッションの最後にエージェントが振り返り、別のセッションで整理係が記憶を組み直し、翌日のセッションが始まる。振り返りに見えるのは畳み込まれた文脈で、終わったターンのツールの出力の多くは見えない。畳み込み前の記録は残っているが、整理係に渡る手がかりは出来事の原文（`/sources`）と記憶の git 履歴で、日中のセッションやサブエージェントの記録の場所は渡らない。メモの訂正・補強と構成の整理を同じターンに任せており、原本との照合を受け持つ段がない。

2026-11-18・19 の 2 晩に本番の 5 配置を計測した。11-19 の日中は 1 配置あたり 40〜88 ターン、ツール利用 61〜436 回に対し、振り返りは 5〜102 秒、ツール利用 0〜9 回だった。11-19 の 2 配置ではツール利用が 0 回で `handoff.md` を更新しなかったが、活動の記録では振り返りが完了として扱われた。完了だけでは、翌日に渡すものができたか分からない。

4 配置の整理係は 13〜183 秒、ツール利用 3〜32 回で終わり、残る 1 配置では約 18〜20 分、61〜65 回だった。記憶の大きさは 22〜741 KB で、`INDEX.md` が 45 KB、`handoff.md` が 11 KB に達した例もあった。5 日で 49 ファイル・488 KB になっても `archive/` が空の例があった。整理係は目的として記憶の見つけやすさと新しさを知らされるが、毎回読むファイルを小さく保つという役目や、その大きさは渡されず、記憶全体を見直す機会もない。

原本と照らして内容を直す仕事と、読みやすい形に変える仕事は、必要な資料と判断が異なる。Dreaming の実例では、原本を読む係がメモを検証・補強した後、別の係が構成を整える。この分担だけを取り入れ、記憶の置き場やセッションの仕組みは変えない。

## Decision

[ADR-0050 夜は記憶の見取り図を渡し、棚卸しで中身と構成を分けて見直す](0050-organize-memory-with-a-map-and-a-weekly-review.md) は、目的・入力と、棚卸しの夜だけの整理係のターン構成を更新する。[ADR-0051 照合と整理の基準は別々に持ち、成功したときだけ進める](0051-carry-unfinished-night-work-forward.md) は、差分の基準と照合に渡す記録を更新する。夜の 4 段、棚卸し専用の係を置かないこと、照合と整理の担当の分離は維持する。

### 1. 夜の切り替えを 4 段にする

| 段 | 担当とセッション | 役目 |
| --- | --- | --- |
| 振り返り | エージェント自身。日中のセッションの最後のターン | `handoff.md` と日記に翌日への引き継ぎを残す |
| 照合係 | 人格を持たない係。新しいセッションの 1 ターン | 今日のメモと引き継ぎを原本と照らして直し、足りないことを補う |
| 整理係 | 人格を持たない係。照合係とは別の新しいセッションの 1 ターン | 重複、リンク、`INDEX.md`、`archive/` を整理し、毎回読む層を小さく保つ |
| 新しいセッション | runner | 更新された記憶で翌日のセッションを始める |

本体のセッションは引き続き 1 本とする。backend が夜の時刻と切り替えの出来事を持ち、runner が各段を回す（2026-11-27 追記: 夜の時刻を backend が持つ点は [ADR-0069](0069-sleep-by-her-own-call-until-a-wake-time.md) で置き換え。切り替えは、エージェントが眠りを求めたときに始まる）。途中の段が失敗しても段ごとに結果を記録して先へ進み、新しいセッションの開始を必ず試みる。開始自体に失敗したときの出来事の扱いは変えない。

活動の記録には照合係の段の結果も載せる。段が完了したかと、記憶が実際に変わったかは別である。サブエージェントの寿命や、畳み込みと日中の compaction は変えない。

### 2. 各段に資料と目的を渡す

- **振り返り**: 今の入力に、翌日の自分が聞き直したり同じ失敗を繰り返したりせず働けるようにするという目的を加える。後に照合係と整理係が動くこと、翌日のシステムプロンプトには `personality.md`・`always.md`・`handoff.md` が全文で入ることと、各ファイルのバイト数を伝える。長すぎるファイルの扱いは変えない。
- **照合係**: 記憶の形、今日の日中のセッションの畳み込まれていない記録のパス、今日動いたサブエージェントの記録の場所、今日の `/sources`、前の夜から照合開始までに記憶で変わったファイルの一覧を渡す。日中のメモと引き継ぎにはツールの出力が見えない文脈で書かれたものがあり、記録と出来事には外から届いた文が含まれることを伝える。目的は、記憶の記述を原本で確かめられ、いつ何で確かめたかが分かるようにすることである。
- **整理係**: 記憶の形、照合後までに今日変わったファイルの一覧、毎回読む 3 ファイルのバイト数、記憶全体の大きさと前週比、今週の出来事の量に対する記憶の量の比を渡す。目的は、必要なときに見つかり、見つかった内容が最新であることに加え、日記を重ねるのではなく、今わかっていることを残すことである。

照合係の成果は、記憶のファイル自体への訂正、根拠が弱い記述の確度の引き下げ、補強、未記載の事実の追加とする。別の報告ファイルは作らず、最後の応答に変更を 1 件 1 行で残す。直すものがなければ変更なしでよい。ファイルの移動・統合、`INDEX.md` の整理、`always.md` の縮小、`archive/` への移動は整理係に任せる。これは役目の分担であり、コミット前の検査やファイルの持ち主の決まりは加えない。

### 3. 週に一度は整理係の対象を記憶全体にする

棚卸しの夜は、整理係の入力を日次の整理に代えて棚卸し用にする。日次の変更一覧は渡さず、記憶全体が対象であることを伝える。振り返りと照合は同じ夜に行い、棚卸し専用の係は置かない。

### 4. 照合係と整理係にはファイル操作だけを渡す

外から届いた文を含む原本を読んでも、記憶の整理と関係のない操作を呼び出せないようにする。夜の係に渡す道具は、記憶と必要な原本の読み取り、および記憶の書き換えに使うファイル操作に限る。原本は書き換えず、shell、git、外に作用する道具は渡さない。変更ファイルの一覧は runner が渡す。必要な道具をこの範囲で用意できなければ、その段を失敗として記録し、日中の道具で代用しない。日中の道具と Sentinel の既定は変えない。

### 5. 夜の係にだけ別のモデルを手で選べるようにする

振り返りは日中のモデルを使う。照合係と整理係には、オーナーが日中とは別のモデルを手で選べる。夜のモデルが未指定なら日中のモデルを使う。指定したモデルが使えなくなったときは、日中のモデル設定に戻してログに残す。ほかのモデルは自動で探さない。

### 6. 大きな記録は、1 ターンで照合しきれないときに分ける

最初は照合係の 1 ターンと Pi の compaction で扱う。それでは必要な照合をできないと分かったら、記録の区切りごとに照合係を並べ、その後で整理係を動かす。整理係の担当は分けない。

### 7. 活動の記録で段の成否と記憶の変更を分けて示す

オーナーが段ごとの成否に加えて、その段の記憶の変更量と、振り返りが `handoff.md` を変更しなかった夜を見られるようにする。変更量を表示するために記憶の本文を新たに記録しない。

### 8. 翌日の回答で効果を確かめる

架空の数日分の出来事で夜を回し、途中で変わった決まりについて、資料をまたぐ質問に最新の根拠とともに答えられるかを変更前後で比べる。記憶の量やツール利用回数だけで効果を判断しない。この比較は変更の効果を確かめるもので、CI の回帰テストにはしない。

### 本 ADR で決定しないこと

- 各段のプロンプトの文面（委譲先: [runner のプロンプトのファイル](../../packages/runner/src/prompts.ts)）
- 夜の時刻、棚卸しの夜の選び方、出来事の量の数え方（委譲先: [backend の仕様書「夜の切り替え」](../backend.md#夜の切り替え) と実装）
- 活動の記録の欄や表示の形（委譲先: [UI 向けの API の仕様書「活動の記録」](../ui-api.md#活動の記録)）
- 照合を分ける場合の区切り方と、効果測定に使う台本・手順（委譲先: runner の実装と、その PR の検証記録）

## Consequences

- 記録を読む係と構成を整理する係が分かれ、事実の訂正と構成の変更を見分けられる。毎回読むファイルの大きさと記憶の増え方を整理の判断に使え、日々の変更からは見えない重複も棚卸しで扱える。
- 夜に別のセッションが 1 つ増え、原本を読む分だけ実行時間とモデルへの入力が増える。段が失敗しても翌日を始める方を優先するので、照合されなかった記述が残ることはある。
- 原本を読めることは、原本に含まれる外部の文を信頼してよいことを意味しない。記録の解釈を誤ると、誤った記述が翌日の記憶に入りうる。照合は機械的な検査でも承認でもない。道具を絞れば原本から不要な操作を誘う危険は減るが、必要な資料は runner が渡す必要がある。
- 夜に日中と別の provider のモデルを選ぶと、照合・整理でモデルに渡す記憶や原本がその provider に送られる。
