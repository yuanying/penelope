# 0017. ターンの入力は 1 行 1 件の JSON を `<events>` で囲み、1 件の型を契約にする

- Date: 2026-11-14
- Status: Accepted

## Context

ADR-0013 で、出来事の中身は backend が `/sources` に追記し、ターンには要約と場所だけを渡すと決めた。何をどう並べて渡すか（ターンに入る形）は、出来事の仕様書に委ねていた。

これまでの runner は、出来事を人の読む文にしてターンに渡していた。1 件ずつ `[seq 12] slack/ops, <時刻>: <要約>` のような見出しの行を置き、その下に足された場所を `<ファイル> lines 4-5, 7-7` の形で続け、出来事の間を空行で区切る。`batch` の出来事は `[batch] slack/ops: 3 events (seq 20, 22, 23)` のように数える。この形には、困ることが 3 つあった。

- 形が runner のコードの中にしか無く、契約になっていない。エージェントが `reply` で答えるときの `in_reply_to` は出来事の `seq` を取るが、その `seq` は見出しの文の中から読み取ることになる。
- オーナーのメッセージの本文はそのまま差し込まれるので、本文に改行や `[seq 1]` のような文字があれば、どこまでが 1 件かが文の形からは決まらない。
- 端から端までのテストは、どの行がどの出来事の場所かを、文から数字を拾って照らしていた。文の書き方を変えると、契約は変わっていないのにテストが壊れる。

natsumi は、ターンの入力を `<events>` の中に 1 行 1 件の JSON を置く形にしている（natsumi ADR 0008）。オーナーは、penelope でも出来事を JSON にして型を決める案を採るとした。

ここで使う言葉は次のとおりである。

- **ターンの入力**: runner が、一度に渡された出来事から作って Pi に渡す 1 つの入力。新しいターンの始まりにも、steer と follow-up にも使う。
- **inline の出来事**: 中身をそのままターンに載せる受信元の出来事（ADR-0013）。
- **`batch` のまとめ**: 一度に渡された `batch` の出来事を、受信元と `stream` ごとに 1 つにまとめたもの。

## Decision

本 ADR は、ADR-0013 の Decision 項 2（ターンには要約と場所だけを渡す）の渡し方を具体にする。何を渡すか（inline の出来事は中身、ほかは要約と足された場所）は変えない。適用範囲は、エージェントの日中のセッションのターンの入力である。夜の振り返りと整理係の入力は出来事から作らないので、対象ではない。

[ADR-0055 残っている仕事は heartbeat の出来事にだけ載せる](0055-show-unfinished-work-in-heartbeats.md) は、heartbeat の JSON の行にだけ残っている仕事を載せる。1 行 1 件の形式と型の契約は変えない。

### ターンの入力は、1 行 1 件の JSON を `<events>` で囲む

- ターンの入力は、`<events>` と `</events>` の間に、1 行に 1 つの JSON を置いたものとする。
- 中身の文字は JSON の文字列の中に入れる。本文に改行があっても、1 件は 1 行に収まる。
- 1 行は、ひとつの出来事か、`batch` のまとめである。`batch` のまとめは、受信元と `stream` ごとに 1 行とし、まとめた出来事の数と `seq` の一覧と足された場所を持つ。

### 1 行の型を契約にする

- 1 行の型を `packages/contract` に置き、それを runner とエージェントとテストの間の契約とする。欄の名前は、sandbox 向けの口と `/sources` の 1 行の欄に揃える。
- 型の欄の意味は、出来事の仕様書に書く。
- テストは、ターンの入力を JSON として読み、欄で照らす。文としての見た目には頼らない。

### 欄の意味を、事実としてシステムプロンプトに書く

- システムプロンプトの出来事と返事の節に、`<events>` の形と各欄の意味を短く書く。どの欄をどう使うかの指図は書かない（ADR-0008）。

### サブエージェントのための余地を残す

- 1 行は、その出来事を受けるエージェントを示す欄を持てるようにする。省けば `main` とする。今はエージェントが `main` だけなので、この欄は書かない。
- この欄は、サブエージェントを作るまでの間、書かれないまま残す。サブエージェントを作るときの ADR で、書くかどうかと意味を決める。

### 畳んだ後も同じ形のまま残る

- 終わったターンを畳むとき（ADR-0015 の Decision 項 1（終わったターンを、送る直前に畳む））、届いた出来事は受け取ったときの形のまま残る。畳んだ後のターンの出来事も `<events>` の形である。

### 本 ADR で決定しないこと

- 1 行の欄の一覧と意味、`batch` のまとめの欄（委譲先: [出来事の仕様書](../events.md) の「ターンに入る形」と `packages/contract` の `src/turn.ts`）
- システムプロンプトの文面（委譲先: プロンプトのファイル `packages/runner/src/prompts.ts`。ADR-0008 の方針に従う）
- サブエージェントの出来事の受け方（委譲先: [sandbox 向けの口の仕様書](../sandbox-api.md) の「出来事を取る」。サブエージェントを作るときの ADR で決める）

## Consequences

- ターンの入力の形が型として 1 か所に決まり、runner とテストとプロンプトが同じものを指す。形を変えるときは、型と仕様書とプロンプトを一緒に変えることになる。
- エージェントは `seq` や足された場所を欄として読める。オーナーの本文がどんな文字を含んでも、1 件の区切りは崩れない。
- テストは欄で照らすので、契約が変わらない限り、文の書き方の違いで壊れない。
- 一方で、人の読む文より字数が増える。欄の名前と引用符が毎行に付き、`batch` のまとめも欄の名前を持つ。量の多い受信元では、その分だけ文脈を使う。
- オーナーのメッセージも JSON の文字列に escape されるので、モデルが読む本文は改行などが `\n` の形になる。
- natsumi の入力と同じ形になるので、natsumi の記録を読む道具やモデルの慣れを持ち込みやすい。

## Alternatives Considered

- **人の読む文のまま、形を仕様書に書いて契約にする**: 本文の中の改行や見出しに似た文字で 1 件の区切りが崩れる問題が残る。テストも文から数字を拾うことになる。
- **出来事ごとに 1 行にし、`batch` もまとめない**: 量の多い流れで、1 件ごとに欄の名前が付いた行が並び、文脈を使う。ADR-0013 で `batch` を流れごとに数えて渡すとした意図に合わない。
